## 1. 背景与问题

灵感来得快、丢得也快。常见的情况：

1. **记了找不到**：想法散在微信收藏、备忘录、便签、聊天记录里，没有统一入口。
2. **只进不出**：收集箱越堆越多，从不回顾，也不判断哪些值得做，最后等于没记。
3. **难以比较**：多个想法摆在一起时，没有统一的评估口径，排优先级全凭当下感觉。
4. **结论不留痕**：一个想法为什么放弃、验证到哪一步了，过段时间就想不起来。

**一句话定位**：一个让想法「**快速进来 → 定期筛选 → 少量落地**」的个人漏斗工具。重点不是"记"，而是把想法**筛**出来。

## 2. 目标用户与使用场景

**MVP 目标用户**：个人使用（独立开发者、产品经理、创作者），一个部署实例服务一个人。团队协作放到后续版本（见第 9 节 Q1）。

| 场景 | 描述 | 频率 |
| --- | --- | --- |
| S1 随手记录 | 路上 / 开会时冒出一个想法，10 秒内记下，不打断当前的事 | 每天多次 |
| S2 定期筛选 | 每周花 15 分钟过一遍收集箱：补充信息、打分，决定推进还是丢弃 | 每周 |
| S3 挑选下一件事 | 想开新项目时，按评分从候选池里挑 | 每月 |
| S4 回顾复盘 | 查看已落地或已放弃的想法及原因，沉淀判断经验 | 不定期 |

## 3. 产品目标与成功指标

| 目标 | 指标（个人自评即可，MVP 不做埋点） |
| --- | --- |
| 记录无摩擦 | 打开页面到保存一条想法 ≤ 10 秒；手机上可用 |
| 收集箱不积压 | 每周筛选后，收集箱里超过 14 天的想法 ≤ 10 条 |
| 决策有依据 | 进入「验证中」及之后阶段的想法 100% 有评分 |
| 结论可追溯 | 归档的想法 100% 填写了结论（落地 / 放弃 + 原因） |

## 4. 核心概念

### 4.1 漏斗阶段（状态机）

```
 收集箱 ──▶ 评估中 ──▶ 验证中 ──▶ 执行中 ──▶ 已落地
 (inbox)   (evaluating) (validating) (building)  (shipped)
    │          │           │           │
    └──────────┴───────────┴───────────┴──▶ 已放弃 (dropped)
```

| 阶段 | 含义 | 进入条件 |
| --- | --- | --- |
| 收集箱 | 刚记下、未处理 | 新建时默认 |
| 评估中 | 值得想一想，补充描述与评分 | 无 |
| 验证中 | 正在做低成本验证（调研、问人、做原型） | **必须已打分** |
| 执行中 | 已决定投入，正式开做 | 必须已打分 |
| 已落地 | 做完了 | 必须填写结论 |
| 已放弃 | 不做了 | 必须填写放弃原因 |

- 阶段可以前进、回退，也可以从任意阶段直接放弃；已落地 / 已放弃的想法可以「重新打开」，回到评估中。
- 每次阶段变更都记一条**时间线日志**（从哪个阶段到哪个阶段、时间、备注）。

### 4.2 评分模型：ICE

| 维度 | 问题 | 取值 |
| --- | --- | --- |
| Impact 影响 | 做成了价值有多大？ | 1–10 整数 |
| Confidence 信心 | 我有多大把握它真的有价值、能做成？ | 1–10 整数 |
| Ease 容易度 | 投入成本有多低？（10 = 很容易） | 1–10 整数 |

- **ICE 总分** = (I + C + E) / 3，保留 1 位小数，**向下截断，不四舍五入**（例：(7+8+8)/3 = 7.666… 显示为 7.6）。
- 前端和后端使用同一套截断规则，不再做二次舍入。
- 三项要么全填，要么都不填；未评分的想法在按评分排序时排在最后。

### 4.3 其他字段

- **标签**：自由输入，可多选，输入时自动补全已有标签。
- **来源**：可选，自由文本（如"读书""用户反馈""洗澡时想到的"）。
- **链接**：可选，多个 URL（参考资料、竞品）。

## 5. 功能需求（MVP）

优先级：**P0** = MVP 必做；**P1** = MVP 尽量做，时间不够可推迟；**P2** = 后续版本。

### 5.1 快速记录（P0）

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F1.1 | 全局快速记录入口：顶部固定输入框 + 快捷键 `N` 唤起 | 任意页面按 `N` 聚焦输入框；回车保存，保存后清空输入框并提示成功 |
| F1.2 | 只有标题必填（1–200 字），其他都可以以后补 | 只填标题即可保存；标题为空时不能提交 |
| F1.3 | 输入框支持行内语法：`#标签` 自动识别成标签 | 输入「做个记账小程序 #工具 #小程序」→ 标题为「做个记账小程序」，标签为 [工具, 小程序] |
| F1.4 | 移动端适配 | 在 375px 宽度下可以完成记录，没有横向滚动 |
| F1.5 | 输入时实时显示识别结果（标题 + 标签） | 输入框下方显示「将会保存为」：标题、标签 |

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| F2.1 | **看板视图**：按阶段分列，卡片显示标题、标签、ICE 分、创建时间 | 6 列（已落地 / 已放弃默认折叠）；卡片可拖拽到其他列 |
| F2.2 | 拖拽换阶段时校验进入条件（4.1） | 把未评分的卡片拖到「验证中」时弹出评分面板，打完分才能完成移动；取消则卡片回到原位 |
| F2.3 | **列表视图**：表格形式，支持排序（创建时间 / 更新时间 / ICE 分） | 各排序方向结果正确；未评分的排最后 |
| F2.4 | 筛选：按阶段、标签（多选）、是否已评分 | 多个条件之间是"且"关系；筛选条件体现在 URL 上，刷新后保留 |


## 7. 非功能需求

### 7.1 安全与权限

- **所有页面和 API 都需要登录**，未登录访问 API 返回 401，访问页面跳转到登录页。
- MVP 认证方案：单用户密码。密码哈希（PBKDF2）存在平台的加密环境变量中；登录成功后下发 HttpOnly + Secure + SameSite=Lax 的签名 Cookie（HMAC），有效期 30 天。
- 登录接口限流：同一 IP 连续失败 5 次后锁定 15 分钟。
- 写操作校验 `Origin` 请求头，防 CSRF；Markdown 渲染前做 XSS 清洗。
- 所有 SQL 使用参数化查询。
- 数据表预留 `owner_id` 字段，为以后支持多用户做准备，不用改表结构。

### 7.2 性能

- 首屏 JS（gzip 后）≤ 200KB；静态资源走 Cloudflare CDN 缓存。
- API 的 P95 响应时间 ≤ 200ms（数据库与函数部署在同一区域）。
- 列表查询必须走索引，使用游标分页，禁止全表扫描后在内存里分页；搜索走 `pg_trgm` 的 GIN 索引（关键词少于 3 个字时 trigram 索引用不上，个人数据量下可以接受）。

### 7.3 可用性

- 支持 Chrome / Safari / Edge 最新两个大版本，以及 iOS Safari。
- 键盘可完成主要操作；交互组件有可访问名称（便于写 E2E 测试）。

## 8. 技术方案（概要）

| 层 | 选型 | 说明 |
| --- | --- | --- |
> **v0.3 调整**：部署目标暂定为 Cloudflare 或 Vercel 之一，所以技术方案改为**与平台无关**：应用代码用 Web 标准 API 编写，每个平台只需要一个很薄的入口文件；数据库改用两个平台都能连的 Postgres（Neon），以后换平台不用迁移数据。

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 运行时 | Cloudflare Workers **或** Vercel Functions | 共用同一个 Hono 应用；入口分别是 `src/entry/cloudflare.ts` 和 `api/index.ts` |
| 后端框架 | Hono | 基于 Web 标准，两个平台都原生支持 |
| 数据库 | Postgres（Neon，走 HTTP 驱动） | 本地开发和测试用 PGlite（进程内 Postgres），不依赖云账号；搜索用 `pg_trgm` 的 GIN 索引 |
| 前端 | React + Vite + TypeScript（SPA） | 构建产物是纯静态文件，两个平台都能托管 |
| UI | Tailwind CSS；拖拽用 dnd-kit | 视觉风格以原型为准 |
| 校验 | Zod（前后端共用 schema） | |
| 测试 | Vitest（单元测试 + 基于 PGlite 的接口集成测试）+ Playwright E2E | |
| 部署 | `wrangler deploy` 或 `vercel deploy`，平台确定后再定 | 数据库迁移使用带日期的 SQL 脚本，内容幂等，手动执行 |

### 8.1 数据模型

以 `migrations/20261029_init.sql` 为准，要点如下：

- `ideas`：`ice_x10` 是生成列，等于 `(I + C + E) * 10 / 3`（整数除法，天然向下截断），用于排序和建索引；三个评分项通过 CHECK 约束保证要么全空、要么全有值。
- `tags` / `idea_tags`：标签对每个用户唯一。
- `idea_events`：时间线（创建、阶段变更、备注）。
- `login_attempts`：按 IP 记录登录失败次数，用于限流。
- 索引：`(owner_id, stage, updated_at)`、`(owner_id, created_at)`、`(owner_id, ice_x10)`，以及标题 + 描述上的 trigram GIN 索引。

### 8.2 API（草案）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/auth/login` · `/api/auth/logout` | 登录 / 登出 |
| GET | `/api/ideas?stage=&tags=&scored=&q=&sort=&cursor=` | 列表 / 筛选 / 搜索（游标分页） |
| POST | `/api/ideas` | 新建 |
| GET / PATCH / DELETE | `/api/ideas/:id` | 详情 / 更新 / 删除 |
| POST | `/api/ideas/:id/stage` | 切换阶段（服务端校验进入条件，写入时间线） |
| POST / DELETE | `/api/ideas/:id/events[/:eventId]` | 添加 / 删除时间线备注 |
| GET | `/api/tags` | 标签列表（用于自动补全） |
| GET | `/api/insights` | 概览统计（P1） |
| GET / POST | `/api/export` · `/api/import` | 导出 / 导入（P1） |

阶段进入条件**必须在服务端校验**，前端校验只用于改善交互体验。
